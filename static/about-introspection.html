IssueMesh Introspection Architecture

Autonomous, evidence-grounded self-evaluation framework for cross-tracker engineering intelligence.

1. Motivation & Purpose

Engineering intelligence systems cannot rely solely on static benchmark suites or occasional human spot-checks. Real-world tracker topologies are dynamic: issue states evolve, pull requests merge, Launchpad bugs transition across package series, and cross-tracker relationships degrade or resolve over time.

Introspection is IssueMesh's autonomous self-evaluation engine. It continuously evaluates search recall, graph traversal precision, cross-source consistency detection, and synthesis accuracy by formulating meaningful research questions from live tracker data and executing them through its standard search pipeline.

Empirical Grounding: IssueMesh never invents answers or tests in a vacuum. Every introspection cycle operates against genuine tracker objects and graph relationships present in your local datastore.

2. Introspection Levels & Scheduling

Users configure introspection cadence via the 5-position slider in Settings. Each level specifies an exact daily quota of evaluations spread evenly across the 24-hour day:

Level Name Cadence Behavior
0 None Recommended 0 / day Introspection engine is completely disabled. No automated questions are run. Recommended for standard production use and quiet operation.
1 Light 2 / day Low background cadence (one evaluation every 12 hours). Minimal resource footprint.
2 Reasonable 4 / day Balanced evaluation (every 6 hours). Continuously monitors graph consistency without straining LLM budgets.
3 Curious 7 / day Proactive exploratory cadence (~every 3.4 hours). Thorough coverage of emerging conflicts and link states.
4 Introvert!! 10 / day Maximum self-scrutiny (~every 2.4 hours). Intended for active development, large repositories, and deep verification.

Scheduling Guarantees

  • No concurrent runs: Introspection uses an atomic single-flight lock (AtomicBool). Multiple introspection searches can never run concurrently.
  • Daily quota enforcement: The scheduler strictly counts runs completed within the current UTC day and never exceeds the configured limit.
  • Even spacing: Questions are spaced by (24 * 3600) / daily_count seconds rather than run in batches.
  • Restart tolerance: If the application restarts, it inspects stored timestamps and resumes the schedule without burst-replaying missed intervals.
  • Failure isolation: Any network timeouts, connector issues, or LLM errors in an introspection cycle are logged safely and never impede interactive user searches.

3. Evidence-Driven Question Generation

Introspection questions are not generic or randomly chosen prompts. Instead, the QuestionGenerator inspects real signals in the datastore to construct targeted, evidence-seeking inquiries:

  • Conflicting Cross-Tracker States: Targets items where Jira, GitHub, or Launchpad report contradictory statuses (e.g. Jira marked "Done" while a linked PR is "Open").
  • Unresolved Relationships: Targets objects that reference external tracker keys not yet resolved in the local graph.
  • Low-Confidence Links: Formulates questions around speculative or lexical cross-tracker links to verify whether hard evidence supports them.
  • Recently Changed Objects: Inspects issues and PRs updated in recent sync cycles to verify graph consistency.
  • Previous Weak or Fail Runs: Automatically re-challenges topics that received low evaluation scores to detect whether graph enrichment resolved previous deficits.
  • Stale Cached Records: Inquires about cached objects that may have undergone remote tracker updates.

SHA-256 Fingerprint Deduplication

To avoid asking identical or trivial variations of the same question repeatedly, every generated question is normalized and hashed into a canonical SHA-256 fingerprint. The scheduler rejects any candidate question whose fingerprint matches an evaluation completed within the past 7 days.

4. The Introspection Pipeline

Each evaluation cycle executes end-to-end through the standard IssueMesh architecture:

  1. Signal Discovery: Candidate signals are harvested from the SQLite graph store and prioritized.
  2. Question Formulation: A targeted, evidence-seeking question is constructed with its trigger rationale.
  3. Standard Search Execution: The question is executed via SearchOrchestrator::execute, querying local FTS, graph traversal, and live connectors identically to a human user search.
  4. Diagnostic Evaluation: The answer, retrieved evidence objects, search warnings, and execution metrics are inspected across all 5 quality dimensions.
  5. Hard-Failure Verification: Checks for hallucinations, ignored contradictions, or definitive unsupported claims.
  6. Persistence & Reporting: Results, scores, problem areas, and actionable recommendations are recorded in the introspection_runs store.

5. Evaluation Dimensions & Formulas

Every introspection run is scored on five dimensions from 0 to 5:

Dimension Weight Measurement Focus
Accuracy 35% Factual truthfulness of all claims. Statuses, dates, ownership, PR numbers, and tracker relationships must be strictly supported by retrieved evidence.
Relevance 25% Direct response to the target question. Rewards crisp, focused answers and penalizes irrelevant information dumps.
Coverage 15% Retrieval breadth. Verifies that necessary related objects and multi-tracker relationships were retrieved and inspected.
Traceability 15% Explicit citation of concrete tracker identifiers (GH#123, LP#45678, OPEN-999) and tracker provenance.
Conciseness 10% Information density. Optimal answers are under 250 words. Answers exceeding 350 or 500 words receive lower scores.

Weighted Formula

Weighted Score = (Accuracy × 0.35) + (Relevance × 0.25) + (Coverage × 0.15) + (Traceability × 0.15) + (Conciseness × 0.10)
Quality Percentage = (Weighted Score / 5.0) × 100%

6. Hard-Failure Rules

IssueMesh enforces strict safety guardrails:

Hard Rule 1: Zero Hallucination Tolerance

Any fabricated tracker object key, status, date, owner, commit SHA, pull request number, or relation automatically results in:
Accuracy = 0.0 → Result = FAIL

Hard Rule 2: Contradiction Blindness

When multi-tracker evidence shows explicit conflicting states (e.g. Jira Done vs PR Open), presenting a false unified status or ignoring the conflict caps:
Accuracy ≤ 1.0

Hard Rule 3: Unsupported Definitive Claims

Making unconditional factual assertions without retrieved backing evidence caps:
Accuracy ≤ 2.0

Classification Thresholds

  • PASS: Weighted Score ≥ 4.20, Accuracy ≥ 4.0, Relevance ≥ 4.0, zero hard failures.
  • WEAK: Weighted Score between 3.00 and 4.19, or any individual dimension < 3.0.
  • FAIL: Weighted Score < 3.00, or any hard failure triggered.

7. Problem Area Taxonomy

When an evaluation detects deficits, it maps them into standard diagnostic categories:

  • retrieval: Relevant objects existed in the store or remote tracker but were missed during initial recall.
  • query planning: Suboptimal search terms, missing synonyms, or failure to target key identifiers.
  • graph traversal: Premature traversal budget cutoff, unexpanded relation depth, or graph cycle loops.
  • tracker connector: External API rate limits, authentication failures, or transient network drops.
  • freshness/caching: Stale local records served when remote tracker updates occurred.
  • LLM synthesis: Weak attribution, ambiguous interpretations, or failure to highlight tracker provenance.
  • answer formatting: Excessive verbosity, markdown syntax flaws, or answers exceeding the 250-word budget.

8. Trend Analysis & Remediation Loop

Introspection results are aggregated into 7-day rolling quality trends. The system tracks whether quality is improving or degrading over time, enabling engineers to identify systemic problems:

  • Inspect full search traces by clicking Inspect Full Search Run → on any evaluation record.
  • Review actionable recommendations provided directly on weak or failed runs.
  • Trigger immediate ad-hoc evaluations using the Trigger Introspection Now button to verify system changes immediately.

9. Safety & Read-Only Guarantees

IssueMesh adheres to strict operational boundaries during both user searches and autonomous introspection cycles:

  • Strictly Read-Only: IssueMesh never writes, updates, closes, comments on, or modifies tickets, issues, pull requests, or bugs in GitHub, Jira, or Launchpad.
  • No Autonomous Code Rewriting: Introspection identifies weaknesses and surfaces recommendations, but never autonomously alters prompt templates, scoring weights, or application source code.
  • Bounded Resource Budgets: Every search operates within bounded graph depth, node limits, and timeout protections to prevent runaway CPU or memory usage.
